# Agent Harness 架构设计题

## 1. Context / Performance 第 2 题

200 轮会话的目标是让下一轮继续理解近期指代和当前约束，同时在用户追问时能找回早期的原话、日期或工具结果。服务端保留会话原文。每次构造模型请求时先计算可用输入预算，给系统指令、工具定义、输出和后续工具结果留空间。达到压缩阈值时，以完整问答轮为单位处理旧历史，保留近期问答原文和本轮工具调用与结果的配对关系。

对旧轮次更新滚动摘要，优先保留已确认事实、最新约束、未解决事项和关键工具结果。摘要项可以关联原会话轮次，方便回查。典型追问如「刚才那个方案」首先用近期原文来解。「半个月前你说的确切时间」触发原文检索，用日期、对象名称和关键词缩小范围。找到依据再带回小段原文。若用户后来改过约束，保留更新时间以区分当时和当前的条件。压缩后的普通对话只需加载较少数据，回查则把额外的耗时和输入放到需要精确证据的轮次。 [Anthropic 上下文工程实践](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

验证时，固定模型和输入预算，在同一批 200 轮历史上依次比较仅近期原文、近期原文加摘要、再加按需回查。检查近期指代是否连贯、早期精确事实是否正确、约束更新能否覆盖旧状态、工具追问能否引用或重新查询正确结果。预先标注参考答案及会话轮次，并记录输入 token、压缩请求开销和响应耗时。这个对照可以识别摘要和回查各自改善了哪些样本。 [LongMemEval](https://arxiv.org/abs/2410.10813)

## 2. Memory 第 1 题

半个月后遇到相似问题时，我会先判断用户要回顾旧回答，还是在当前条件下重新求解。两种意图都只检索同一用户已授权纳入记忆的会话。候选记录带原始出处、会话时间和事实生效时间。先限定授权范围，再结合语义和关键词检索。用户明确说「上周」或「半个月前」时，把时间范围用于过滤或排序。只有通过授权过滤的候选才能放入模型上下文。 [LongMemEval 时间感知检索](https://arxiv.org/html/2410.10813v2#S5.SS4)

如果用户问「上次怎么说」，可以引用对应日期和简短原话。如果问「现在怎么办」，先核对当前约束和旧信息的有效期，再决定哪些旧内容有参考价值。例如用户曾希望选择费用最低的活动，现在明确要求周末有场次，应按当前条件比较。旧回答中的活动价格若可能变化，须重新查询当前来源。两个历史记录冲突且会改变结论时，问用户采用哪个条件。证据不足时说明无法确认当时的回答。

验收至少包含偏好后来更新、旧事实后来过期、用户实际没有问过这三类样本。分别检查候选是否找到，以及最终回答是否正确区分了历史和当前。一次召回命中只能说明检索成功，回答本身还需要核对信息的时间和来源。 [LongMemEval](https://arxiv.org/abs/2410.10813)

## 3. Task 第 1 题

设任务为跨模块重构，约束是保持公开接口兼容，验收需要回归通过。长任务中常见的偏离是模型把「局部代码已经清理」看成完成，忽略旧调用者或遗漏接口检查。下面三种措施分别作用在不同环节。

| 方案 | 优点 | 代价和适用场景 |
|---|---|---|
| 在关键模型请求中重申目标与约束 | 简单，能让下一步直接看到原目标 | 提示反复占用上下文，也无法独立证明接口兼容。适合短任务或辅助提醒。 |
| 在上下文之外持久化目标、约束、计划与进度 | 切换上下文或恢复任务时，可以从明确的状态继续 | 需要更新和版本管理。若进度全由模型自行填写，仍可能提前宣告完成。 |
| 在关键阶段验收 | 用接口检查和回归结果发现行为偏差 | 检查有开销，且只能覆盖已定义的约束。适合在关键变更后和最终交付前运行。 |

我的主方案是把持久化任务状态和阶段验收结合。任务状态存目标、用户确认的约束、下一阶段和验收标准。每次开始阶段时把相关约束放回上下文，阶段结束后以实际检查结果更新进度。如果失败，保存失败项和证据，再调整计划。需要放宽兼容约束时，由用户确认目标或约束变更。最终验收可在故意引入一处接口破坏的样本上验证，即使代码可运行，检查也应该阻止任务被标为完成。 [Anthropic 长程 Agent 实践](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)

## 4. Tool / Session Runtime 第 2 题

每个 session 同时有一个活跃对话轮。普通新消息写入会话队列后立即确认已接收，按到达顺序等待。显式取消作为控制事件，指向被取消的运行。异步完成事件带会话 ID、运行 ID、工具调用 ID 和事件 ID。Runtime 将事件送到所属运行，串行更新同一个 session 的状态。运行等待的工具结果可以直接推进该轮，即使普通消息已经在排队。 [Orleans 请求调度](https://learn.microsoft.com/en-us/dotnet/orleans/grains/request-scheduling)

完成事件可能重复或迟到。每次应用完成事件时，将已消费事件的记录与状态更新一起提交。重复事件返回同一处理结果。若运行已取消或超时，迟到结果记到原运行，原运行保持终态。取消时尝试停止仍在运行的工具，已经生效的外部变更按事实提示用户。等待设置超时，避免工具结果一直不到导致整个会话无法继续。 [Microsoft Durable Task 外部事件](https://learn.microsoft.com/en-us/azure/durable-task/common/durable-task-external-events)

用三条时间线验证。第一条先收到新消息，再收到当前轮等待的结果，检查旧轮继续并结束后才启动新轮。第二条在取消后收到迟到结果，检查结果归档、提示已生效变更以及会话正常前进。第三条重复投递同一结果，检查只更新一次状态和只触发一次继续执行。

## 5. Agent Runtime 架构对比第 1 题

共用一个只读场景。模型需要读取 `event.txt` 中的活动开始时间。成功返回「14:30」，失败时文件不存在。Claude Code 的公开文档说明它负责提供工具、管理模型可见上下文并按权限规则执行。用户可以在产品中看到运行过程并中断。这个产品行为可用来解释 Harness 的职责。API 文档可用来核对客户端工具的消息契约。 [Claude Code 工作方式](https://code.claude.com/docs/en/how-claude-code-works)

| 维度 | Claude Messages 客户端工具 | GLM 和豆包的 Chat Completions 函数调用 |
|---|---|---|
| 工具定义 | 描述工具并提供 `input_schema` | 通过 `tools` 注册函数，参数规范在 `function.parameters` |
| 模型发出调用 | assistant 内容中的 `tool_use` 块，含 ID 和对象类型的 `input` | assistant 消息中的 `tool_calls`，函数参数在 JSON 字符串 `function.arguments` |
| 成功回传 | user 消息的 `tool_result` 块，用 `tool_use_id` 关联，内容含「14:30」 | `role=tool` 的消息用 `tool_call_id` 关联，内容含「14:30」 |
| 失败回传 | 同一个结果块设置 `is_error`，并提供找不到文件的说明 | 在对应的工具消息 `content` 中封装应用约定的结构化错误，例如 `file_not_found` |

Claude Messages 要求工具结果紧跟对应的调用消息，并位于回传消息的内容数组前端。适配器需要维护块的类型和顺序，换来协议中可直接表达工具失败等信息。对采用同一 Chat Completions 核心字段的服务，接入方可以复用工具定义和结果配对逻辑。参数仍要解析和校验，错误内容及供应商扩展也需要按接口验证。两种协议在这个客户端工具案例中都由接入方实际执行工具。对照示例检查两条链路能否保持同一个调用 ID，以及模型是否拿到足以继续或解释失败的信息。 [Claude 工具定义](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools) · [Claude 结果与错误回传](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls) · [GLM 工具调用](https://docs.bigmodel.cn/cn/guide/capabilities/function-calling) · [火山方舟 Chat API](https://docs.volcengine.com/docs/ark/chat-api?lang=zh)
